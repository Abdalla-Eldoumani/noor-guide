# Internationalization

This document describes the localization plan for Noor Guide. The Arabic locale is partially scaffolded but not yet wired into the runtime; this document describes both the current state and the intended end state so that whoever picks the work up next can finish it without guessing.

## Current state

The repository contains two hand-authored translation files:

- `messages/en.json` (English UI strings, around 9.8 kB)
- `messages/ar.json` (Arabic UI strings, around 12.6 kB)

These files are present at the repository root. They were authored by the project's translators and are treated the same way `src/data/content/*.json` is treated: as authored, reviewed source material that is not regenerated or paraphrased by an agent.

`next-intl` is not yet installed. There is no `[locale]` segment under `src/app/`. The locale switcher is not yet present in the header. The active route structure is still `/`, `/learn/*`, `/tools/*`, `/progress`. The whole site renders in English. Arabic translations sit in the repo waiting to be wired up.

## Intended end state

Once `next-intl` is installed and configured, the URL structure becomes:

- `/`, `/learn`, `/learn/aqeedah`, `/tools/prayer-times`, etc. for English (the default locale, no URL prefix).
- `/ar`, `/ar/learn`, `/ar/learn/aqeedah`, `/ar/tools/prayer-times`, etc. for Arabic.

Routing uses `next-intl`'s `localePrefix: "as-needed"` setting, which keeps English at the root and prefixes Arabic with `/ar`. Pages move from `src/app/<route>` to `src/app/[locale]/<route>`. The root layout reads the active `locale` parameter, sets `<html lang="ar" dir="rtl">` for `/ar/*`, and conditionally loads IBM Plex Sans Arabic via `next/font/google` for the Arabic UI chrome.

The active locale is persisted in `noor-settings.language` (a field that already exists in the settings shape), so a return visitor lands on the correct locale automatically. A `LocaleSwitcher` component in the header swaps `/foo` ↔ `/ar/foo` and writes the chosen locale back to settings.

## What gets translated and what doesn't

This is the most important rule and the easiest one to get wrong:

- **UI chrome is translated.** Navigation labels, button text, page intros, empty states, error messages, breadcrumbs. These strings live in `messages/{en,ar}.json` and are looked up via `useTranslations()`.
- **Religious content is not translated and not retranslated.** Quran translations, hadith translations, dua translations, and Arabic source text in `src/data/content/*.json` came in pre-verified by the human authors. They render the same in both locales. The Arabic source text in those files is the original; the English translations are the scholarly translations the authors selected. Neither is regenerated.
- **Educational instructional prose is not yet translated.** The `description_en`, `instruction_en`, `content_en`, `key_points`, and `notes` fields inside `src/data/content/*.json` were written by the project's authors as the teaching content. Those strings render in English on `/ar` pages, surrounded by Arabic UI chrome. This is the intended state for the initial Arabic launch, not a bug.

## How to add a new UI string

1. Pick a key namespace appropriate to the surface (for example `nav.learn` or `home.hero.title`).
2. Add the key to `messages/en.json` with the English value.
3. Add the same key to `messages/ar.json` with the Arabic value (have the human translators write it; do not machine-translate).
4. In the component, `const t = useTranslations("nav")` and call `t("learn")`.

If a string is genuinely UI-only (a button label, a page heading), it goes in the messages files. If it is religious or educational content, it stays in `src/data/content/*.json` and is not retranslated.

## RTL mirroring

When `dir="rtl"` is active, several UI patterns mirror automatically through CSS logical properties (`border-s-*`, `ps-*`, `me-*`, etc.). A few patterns need explicit attention:

- Previous/next navigation arrows reverse direction
- Breadcrumb chevron separators reverse
- The progress bar fill grows from the right edge
- The header logo's component order may need a flip
- The bottom mobile nav icon order may need review

Any new component that uses directional Tailwind utilities (`pl-*`, `pr-*`, `ml-*`, `mr-*`, `border-l-*`, `border-r-*`) should be reviewed and switched to logical equivalents (`ps-*`, `pe-*`, `ms-*`, `me-*`, `border-s-*`, `border-e-*`) before the locale work lands.

## Future Arabic instructional prose pass

A later pass can add Arabic versions of the educational prose. The plan: each instructional field in `src/data/content/*.json` (such as `description_en`, `instruction_en`, `content_en`, `key_points`, `notes`, `priority`) gains a sibling field with the `_ar` suffix (`description_ar`, `instruction_ar`, etc.). The rendering layer in `src/lib/content.ts` and the consuming components prefer the `_ar` field when the active locale is Arabic and fall back to `_en` when no Arabic field is present. Items can therefore be translated incrementally without breaking partial coverage.

That work requires a knowledgeable Arabic-fluent reviewer. It is out of scope until such a reviewer is involved. Until then, the English instructional prose renders unchanged on the Arabic site, and that is the correct, intended state.

## Mixed-direction edge cases

A few specific cases come up in mixed Arabic-Latin contexts:

- **Latin source names inside Arabic UI** (`Sahih Bukhari 6312` rendered next to Arabic text) should keep their Latin direction; wrap them in `<span dir="ltr">` if they break.
- **Western numerals inside RTL paragraphs** generally render correctly because of Unicode bidi rules. Confirm visually if a paragraph contains mixed scripts.
- **The prayer times table on `/ar/tools/prayer-times`** mixes Arabic prayer names (الفجر, الظهر, etc.) with Latin time strings (`05:23`, `13:08`). This is fine; the bidi algorithm handles it. Set `dir="rtl"` on the table cells that contain the Arabic name and let the time string sit in its own cell.
