# Internationalization

Noor Guide runs in three locales: English at `/`, Arabic at `/ar`, French at `/fr`.
This document covers how they are wired, what the rules are, and how the build stops a
locale gap from shipping.

## Routing

`next-intl` with `localePrefix: "as-needed"`, so English is unprefixed.

- `src/i18n/routing.ts` declares the locales. Adding one here is the single source of
  truth; the language switcher iterates it, so a new locale appears automatically.
- `src/i18n/navigation.ts` exports locale-aware `Link`, `useRouter`, `usePathname`. Use
  these everywhere. Importing from `next/link` drops the locale on navigation, which is a
  bug that has shipped here before.
- `src/i18n/request.ts` loads `messages/${locale}.json`.
- `src/proxy.ts` is the middleware (the Next 16 filename).

The active locale is persisted to `noor-settings.language` so a returning visitor lands on
the right prefix.

## Two places strings live

**`messages/{en,ar,fr}.json`** hold UI chrome: navigation, buttons, headings, empty states,
error messages, breadcrumbs. Read with `useTranslations` in client components and
`getTranslations({ locale, namespace })` in server components.

**`src/data/content/*.json`** hold educational content. Fields use one of two naming
styles, and both are read through `pickLocalized` (server) or `useLocalizedContent`
(client):

- Suffixed: `title_en`, `title_ar`, `title_fr`
- Bare-named with siblings: `definition`, `definition_ar`, `definition_fr`

Never read a content field directly. `{item.definition}` renders English on every locale;
`{pick(item, "definition")}` renders the right one.

## What is translated and what is not

**Project prose is translated.** Module descriptions, lesson instructions, step text,
key-point lists, glossary definitions, usage notes, all UI copy. These are the project
authors' words.

**Scripture is not translated here.** Quran and hadith text come from verified sources in
every locale:

| | Arabic | English | French |
|---|---|---|---|
| Quran | Uthmani | Saheeh International | Hamidullah |
| Hadith | `hadeeth_ar` | `hadeeth` (en) | `hadeeth` (fr) |

Hadith text in all three languages comes from a single Encyclopedia of Translated Prophetic
Hadiths entry, so the locales carry the same meaning by construction rather than by review.
`scripts/fetch-scripture.mjs` pulls both; `src/data/hadith-mapping.json` maps each cited
hadith to its encyclopedia id.

That mapping is currently unpopulated. Until a reviewer fills it in and the fetch runs,
hadith text renders in the English translation the project authors selected, with the
citation and grading localized. Run `npm run fetch:scripture` from a machine with network
access to populate it.

Transliteration and back-translation are suppressed on `/ar`, since an Arabic reader
already has the source. See `ArabicText`.

## The three defect classes

Every locale bug seen in this project has been one of three, and they need different fixes.
Knowing which one you are looking at saves time.

1. **Data missing.** Nothing to render. Author the translation.
2. **Data present, component ignores locale.** The translation exists in the repo and the
   component reads the wrong field. The glossary shipped 96 English definitions on `/ar`
   while `definition_ar` sat unused. This is the cheapest to fix and the easiest to miss.
3. **Component never wired to i18n.** Hardcoded literals. The entire `/tools` surface, four
   pages and four components, had zero `useTranslations` calls.

## The gates

```bash
npm run verify:i18n      # static, no server, runs automatically before build
npm run verify:locales   # render-time, needs a running server
```

`verify:i18n` fails on key-set drift between the three catalogues, empty values,
placeholder mismatches (`{count}` present in one locale and absent in another), an Arabic
value with no Arabic characters, a French value containing Arabic, a value that merely
repeats the English, and any content field carrying `_en` or `_ar` without a full set of
siblings. It catches classes 1 and 3 and gates the build.

`verify:locales` renders every route in every locale and flags text whose script disagrees
with the locale. It catches class 2, which no linter can see: the string is present and
correctly translated, just read from the wrong field.

```bash
LOCALES=ar,fr node scripts/verify-locales.mjs http://localhost:3000 / /learn /tools
```

Both read `scripts/i18n-allowlist.json`, so every deliberate exception is one reviewable
line rather than a loosened rule.

### What the render scan cannot see

`verify-locales.mjs` fetches server-rendered HTML. Components pulled in through
`dynamic()` are not in that HTML, so their strings are invisible to it.
`SurahPlayer` and `MemorizationHelper` are both lazily loaded, and both shipped with
hardcoded English button labels that the scan reported as clean. When you add a
`dynamic()` import, check its strings by hand or move them into a component that
renders on the server.

## Marking intentional foreign script

Text deliberately rendered in another script must carry `lang` and `dir`:

```tsx
<p dir="rtl" lang="ar" className="font-arabic">الوضوء</p>
<span dir="ltr">Sahih Muslim 225</span>
```

This is what makes a screen reader switch voice mid-page, and `verify:locales` uses the
same attribute as the signal that the text is intentional. Unmarked foreign-script text is
reported.

## Adding a locale

1. Add the code to `routing.ts`.
2. Add its label to `LABELS` in `LocaleSwitcher.tsx`. The `Record<Locale, string>` type
   makes this a compile error until you do, which is intentional.
3. Copy `messages/en.json` to `messages/<code>.json` and translate every value.
4. Add `<field>_<code>` siblings across `src/data/content/*.json`.
5. Add the code to `ALTERNATE_LOCALES` in `src/app/sitemap.ts`.
6. Run `npm run verify:i18n` until clean, then `verify:locales` against a running server.

## RTL

Use logical properties (`ps-`, `pe-`, `ms-`, `me-`, `start-`, `end-`, `border-s-`) rather
than physical ones. Mirror directional icons with `rtl:rotate-180`. Arabic UI body text
uses IBM Plex Sans Arabic; Quranic and classical Arabic keeps Amiri via `font-arabic`.

French strings run roughly 15 to 20 percent longer than English, so check that headings and
buttons still fit at 375px after adding French copy.
