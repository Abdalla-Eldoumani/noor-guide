# Internationalization

This document describes how the Arabic locale is wired into Noor Guide and where to look when adding strings, debugging routing, or extending coverage.

## Current state

The site runs under two locales: English (the default, served at `/`) and Arabic (served at `/ar`). Routing is handled by `next-intl` with `localePrefix: "as-needed"`. Pages live under `src/app/[locale]/`, the middleware at `middleware.ts` rewrites the default locale to its prefixed form internally, and the layout at `src/app/[locale]/layout.tsx` sets `<html lang="ar" dir="rtl">` for Arabic routes.

Two hand-authored translation files drive the UI:

- `messages/en.json` (English UI strings)
- `messages/ar.json` (Arabic UI strings)

They were authored and reviewed by the project's translators. Like `src/data/content/*.json`, they are not regenerated or paraphrased by an agent.

The active locale is persisted in `noor-settings.language` so a return visitor lands on the correct prefix automatically. The header includes a `LocaleSwitcher` component (`src/components/layout/LocaleSwitcher.tsx`) that swaps `/foo` ↔ `/ar/foo` while preserving the current path and writes the choice back to settings.

## Routing primitives

- `src/i18n/routing.ts` declares the locales and `localePrefix: "as-needed"`.
- `src/i18n/navigation.ts` exports a locale-aware `Link`, `useRouter`, and `usePathname`. Use these everywhere instead of `next/link` and `next/navigation` so internal navigation preserves the active locale.
- `src/i18n/request.ts` loads `messages/${locale}.json` per request.
- `next.config.js` is wrapped with `next-intl/plugin`.

## Locale-aware content rendering

Religious data and educational instructional prose live in `src/data/content/*.json`. The rendering layer reads those fields through `pickLocalized()` from `src/lib/content-i18n.ts`, which prefers `${field}_${locale}` when present and falls back to the bare field or `_en` suffix otherwise. The companion hook `useLocalizedContent()` binds that lookup to the active locale for client components.

The convention for adding Arabic content to a JSON entry:

- Suffixed fields (`title_en` already exists) gain a sibling `title_ar`. Lookup picks `title_ar` first on `/ar`.
- Bare-named fields (`key_points`, `notes`, `prerequisites`, `description`) gain a sibling with the `_ar` suffix (`key_points_ar`, `notes_ar`, etc.). Lookup picks the suffixed form first on `/ar`, falls back to the bare form otherwise.
- The TypeScript shapes in `src/types/content.ts` already declare these `_ar` siblings as optional, so authors can add them incrementally without breaking compilation.

When an Arabic field is missing, the component falls back to the English source unchanged. There is no placeholder, no machine translation, and no AI-generated text inserted; whatever the human translators have authored is what users see.

Components that already consume the locale-aware lookup: every lesson client (Aqeedah, Pillars, Wudu, Salah, Surahs, Duas), the home page module list, the learn dashboard, and the lesson card. The Header, Footer, MobileNav, Breadcrumb, and other UI chrome read from `messages/{en,ar}.json` via `useTranslations`.

## What gets translated and what doesn't

There are two tiers, and the boundary is bright.

**Tier A: project-author prose, translated.** Module descriptions, lesson introductions, step instructions, prerequisite lists, key-point bullets, breaker descriptions, dua context labels, prayer-time descriptions, surah priority labels, glossary definitions, Arabic-phrase usage notes. These are the framing and instructional prose the project authors wrote in English. Arabic siblings (`description_ar`, `instruction_ar`, `content_ar`, `key_points_ar`, `notes_ar`, etc.) live next to the English source in `src/data/content/*.json`. The rendering layer prefers the Arabic on `/ar` and falls back to English when an Arabic field is missing.

**Tier B: religious-source content, not retranslated.** Quran verse English translations (`translation` on a verse), hadith full English text (`text_en` on a hadith source), dua English translations (`translation` on a dua), Quran-reference translations on aqeedah/pillars items. These are scholarly English translations the human authors selected from authentic editions. They are not retranslated by AI on `/ar`. Instead, the rendering layer suppresses the redundant blocks on `/ar`:

- `ArabicText` (used for Quran verses, dua text, and salah recitations) hides the transliteration and translation blocks on `/ar`. An Arabic reader sees the verse or dua in its original Arabic; transliteration is a pronunciation guide for English speakers, and translation is a back-translation of the same Arabic, so neither adds value.
- `HadithBlock` checks for Arabic characters in the supplied hadith text. On `/ar`, when the text is the English fallback (no Arabic characters present), only the source reference renders. When a future translator adds Arabic hadith text, it appears in place.

The result on `/ar`: every page reads in Arabic prose for framing and instructions, with Quran verses and hadith quotations rendered in the original Arabic source, accompanied by Arabic-script source references like "صحيح البخاري ٦٣١" once those references land. The transliteration and English-translation blocks visible on `/` are intentionally absent on `/ar`.

## How to add a new UI string

1. Pick a key namespace appropriate to the surface (for example `nav.learn` or `home.hero.title`).
2. Add the key to `messages/en.json` with the English value.
3. Add the same key to `messages/ar.json` with the Arabic value (have the human translators write it; do not machine-translate).
4. In the component, `const t = useTranslations("nav")` and call `t("learn")`.

If a string is genuinely UI-only (a button label, a page heading), it goes in the messages files. If it is religious or educational content, it stays in `src/data/content/*.json` and is not retranslated.

## RTL mirroring

When `dir="rtl"` is active, several UI patterns mirror automatically through CSS logical properties (`border-s-*`, `ps-*`, `me-*`, etc.). A few patterns need explicit attention:

- Previous/next navigation arrows reverse direction
- Breadcrumb chevron separators reverse
- The progress bar fill grows from the right edge
- The header logo's component order may need a flip
- The bottom mobile nav icon order may need review

Any new component that uses directional Tailwind utilities (`pl-*`, `pr-*`, `ml-*`, `mr-*`, `border-l-*`, `border-r-*`) should be reviewed and switched to logical equivalents (`ps-*`, `pe-*`, `ms-*`, `me-*`, `border-s-*`, `border-e-*`) before the locale work lands.

## Future Arabic instructional prose pass

A later pass can add Arabic versions of the educational prose. The plan: each instructional field in `src/data/content/*.json` (such as `description_en`, `instruction_en`, `content_en`, `key_points`, `notes`, `priority`) gains a sibling field with the `_ar` suffix (`description_ar`, `instruction_ar`, etc.). The rendering layer in `src/lib/content.ts` and the consuming components prefer the `_ar` field when the active locale is Arabic and fall back to `_en` when no Arabic field is present. Items can therefore be translated incrementally without breaking partial coverage.

That work requires a knowledgeable Arabic-fluent reviewer. It is out of scope until such a reviewer is involved. Until then, the English instructional prose renders unchanged on the Arabic site, and that is the correct, intended state.

## Mixed-direction edge cases

A few specific cases come up in mixed Arabic-Latin contexts:

- **Latin source names inside Arabic UI** (`Sahih Bukhari 6312` rendered next to Arabic text) should keep their Latin direction; wrap them in `<span dir="ltr">` if they break.
- **Western numerals inside RTL paragraphs** generally render correctly because of Unicode bidi rules. Confirm visually if a paragraph contains mixed scripts.
- **The prayer times table on `/ar/tools/prayer-times`** mixes Arabic prayer names (الفجر, الظهر, etc.) with Latin time strings (`05:23`, `13:08`). This is fine; the bidi algorithm handles it. Set `dir="rtl"` on the table cells that contain the Arabic name and let the time string sit in its own cell.
